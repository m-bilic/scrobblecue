# ScrobbleCue – Project Plan

> Scrobble your vinyl to Last.fm with as few taps as possible, using your Discogs collection.
> Android app + website first, iOS later. An open-source portfolio and learning project.

_Last updated: 2026-10-27_

This plan covers goals, roadmap and organisation. **How** the system is built – decisions with alternatives, what lives where and why, API, flows and rules – is in the [technical specification](SPEC.md).

---

## 1. Goals

- **Minimal taps.** Scrobbling a side of a record should take 1–2 taps from the home screen.
- **A tool, not a service.** No accounts and no user data on the server – users connect Last.fm and Discogs, and everything else stays on their device.
- **Android app on Google Play** and a **website**, sharing one stateless backend.
- **iOS later** – shared logic lives in the backend so an iOS app is mostly screens.
- **Open-source portfolio project** – public from day one, using modern, industry-standard tools and doing things properly (tests, CI, documentation).

### Non-goals (for now)
- No audio playback or recognition – ScrobbleCue only sends metadata.
- No syncing of corrections or play logs between devices.
- No social features.

## 2. Key decisions (summary)

Full reasoning and alternatives: [SPEC.md, section 3](SPEC.md#3-decisions).

| Topic | Decision |
|---|---|
| Name | **ScrobbleCue** (scrobblecue.com / scrobblecue.app) |
| Backend | Java 25 + Spring Boot 4, **stateless – no database, stores nothing** |
| Android | Kotlin + Jetpack Compose, package `com.scrobblecue.app` |
| Web | React + TypeScript (Vite), React Router, TanStack Query, Dexie |
| iOS (later) | SwiftUI on the same API |
| API | OpenAPI generated by the backend; clients generated from it; versioned under `/v1` |
| User credentials | Sealed (encrypted) bundle stored on the user's device; app secrets only on the server |
| Discogs | Option A: backend signs and forwards login + collection requests without storing them; public tracklists fetched by clients directly. Option B later if needed |
| User data | Collection, corrections, play log and scrobble queue on the device only |
| Live mode | Runs on the device (Android: WorkManager; web: while the tab is open) |
| Duplicates | Client queue + check against Last.fm's recent scrobbles before uncertain retries |
| Track lengths | Discogs → MusicBrainz → Last.fm → default 3:30, user correction wins |
| v1 scope | Side-based scrobbling for vinyl; other formats whole/selected tracks |
| Collection sync | Once after connecting Discogs, then manual |
| Repo / license | Monorepo, MIT |

## 4. How it is developed

- **Maintainer:** product decisions, review, testing on real devices and turntables, API accounts and secrets, releases and all commits.
- **Code generation:** code, tests, CI configuration and documentation are generated with Claude Code under the maintainer's direction.
- **Release requirements:** a Google Play closed test with 12 testers for 14 days (required for new personal developer accounts), and prior approval from Last.fm for public pages that use its API (email to partners@last.fm with screenshots of the "powered by AudioScrobbler" placements).

## 5. Open source & portfolio

**Repository**
- Public GitHub repo from day one, with a clean, descriptive commit history.
- License: **MIT**. The license grants no rights to the "ScrobbleCue" name; forks should rename.
- Secrets never committed: `.env` is git-ignored, `.env.example` lists the names only. GitHub secret scanning + push protection enabled.
- Production secrets live only in the hosting provider's secret store and in GitHub Actions secrets.

**Hosting model**
- **One official instance**, run by the maintainer: the backend behind `api.scrobblecue.app`, used by the Google Play app and the website at `scrobblecue.app`. Users just install the app or open the website and connect their accounts – no server, no API keys, no setup.
- **Self-hosting is optional**, for developers and contributors: run the backend with your own Last.fm and Discogs API keys (`./gradlew bootRun`), documented in the README.

**Portfolio polish**
- README with screenshots/GIF, architecture diagram, tech stack, and "run it locally" steps.
- CI badges (build, tests) and test coverage.
- `docs/decisions/` – short architecture decision records (ADRs).
- `CONTRIBUTING.md`, issue templates, and a `CHANGELOG.md` per release.

## 7. Risks & open questions

- **"Scrobble" trademark** – widely used by third-party apps, but unverified. Check before launch, and ask in the Last.fm approval email.
- **Last.fm API access** – Last.fm may end access at any time, with or without cause, and public pages need its prior approval. Keep the attribution rules from [SPEC.md section 17](SPEC.md#17-third-party-api-terms) and get approval before launch.
- **Discogs rate limit on the server IP** (Option A) – fine at small scale (~86,000 requests/day). If it becomes a problem, switch to Option B; email Discogs API support first.
- **Large collections** – a first sync of several thousand records takes a few dozen requests; show progress and keep the app usable meanwhile.
- **Missing durations** – affect live-mode timing. Fallbacks and corrections mitigate this.
- **Background limits** – Android may delay WorkManager jobs and browsers throttle background tabs. Timestamps are fixed up front, so scrobbles stay correct; only "now playing" can lag. Web live mode needs the tab open (unsent scrobbles go out on the next visit).
- **Sealing key loss** – if the server's credential keys are lost, every user must reconnect. Store them in the host's secret store and keep an offline backup.
- **Hosting choice** – decide in phase 7. Needs HTTPS + custom domain; EU region preferred.
- **Android package name** – `com.scrobblecue.app` is permanent once published.
